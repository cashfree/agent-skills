This file lists topics real-world Cashfree integrators hit in production that
the current skill set does NOT cover (or covers only incidentally). It is
ordered by business impact — the earlier items unblock the widest merchant
scenarios and will surface most often in prod support tickets.

For every gap we note:
  • What it is / why devs need it
  • Cashfree API / product surface that backs it
  • Whether to EXTEND an existing skill or CREATE a new one
  • Suggested skill filename if new
  • Rough priority (P0 = ship next, P1 = next quarter, P2 = nice-to-have)

Legend for current state (from audit of src/templates/):
  YES      = fully covered in an existing SKILL.md / REFERENCE.md
  PARTIAL  = mentioned in passing; not a first-class section
  NO       = not present anywhere

1. SETTLEMENTS & RECONCILIATION                                         [x] DONE
   (shipped 2026-04-19 — src/templates/settlements-and-reconciliation.md
    + settlements-and-reconciliation-reference.md; wired in index.ts + manifest.ts
    + README.md; installs as settlements-and-reconciliation/SKILL.md + REFERENCE.md)
   Current: PARTIAL. pg/webhooks mentions SETTLEMENT_WEBHOOK and pg/api-reference
            lists rate limits for "Get Settlements". No end-to-end doc for the
            settlement lifecycle, recon APIs, or UTR → bank-statement matching.
   Why devs need it: Finance ops files this under "we went live, now where is
            my money and how do I reconcile it against the bank". Unblocks
            accounting integration (Tally, QuickBooks, Zoho Books, SAP) and
            auto-ledger updates. Every live merchant asks about T+1 vs instant,
            TDS deduction, and "why is the settled amount less than the order
            amount" within the first settlement cycle.
   Cashfree surface:
     • GET  /pg/settlements                      (list settlements)
     • GET  /pg/orders/{order_id}/settlements    (per-order)
     • POST /pg/settlement/recon                 (cursor-paginated recon)
     • POST /pg/recon                            (transaction-level recon)
     • Webhooks: SETTLEMENT_SUCCESS, SETTLEMENT_WEBHOOK
     • Dashboard MIS reports: Transactions, Settlement, Settlement Recon,
       Ledger, Vendor Recon, Refunds — CSV / XLSX / scheduled SFTP
     • Instant Settlements product (fee model, on-demand endpoint)
   Action: CREATE new skill — `settlements-and-reconciliation/`
           (SKILL.md + references/REFERENCE.md with full response shapes,
           TDS/fee breakdown, UTR matching example, instant-settlements flow)
   Priority: P0


2. REFUNDS — DEDICATED SKILL                                            [x] DONE
   (shipped 2026-04-19 — src/templates/pg/refunds.md + pg/refunds-reference.md;
    wired in pg.ts + index.ts + manifest.ts + README.md; installs as
    pg/refunds/SKILL.md + pg/refunds/references/REFERENCE.md)
   Current: PARTIAL. Refund basics are in pg/api-reference.md Workflow D, but
            there is no dedicated skill covering refund policy (instant vs
            normal speed, partial, multi-refund, reverse pre-auth vs void,
            refund failure reasons, refund webhook deduping, merchant-provided
            refund_id collisions). Common-mistakes has none.
   Why devs need it: Refunds are the #2 support-ticket generator after
            webhooks. Questions: "can I refund to a different instrument?",
            "why is refund PENDING for 3 days?", "instant refund fee?",
            "refund reversed — what now?", "refund vs void for pre-auth?".
   Cashfree surface:
     • POST   /pg/orders/{order_id}/refunds                  (create)
     • GET    /pg/orders/{order_id}/refunds                  (list for order)
     • GET    /pg/orders/{order_id}/refunds/{refund_id}      (fetch)
     • Webhooks: REFUND_STATUS_WEBHOOK (SUCCESS / FAILED / PENDING / CANCELLED)
     • Speeds: STANDARD vs INSTANT refunds (different fee + eligibility)
     • Refund reason codes and retry semantics
   Action: CREATE new skill — `pg/refunds/` (SKILL.md + REFERENCE.md).
           Promote the existing content from pg/api-reference §D into a
           full skill; add instant-refund eligibility logic and
           idempotency (refund_id uniqueness) rules.
   Priority: P0

===============================================================================
  NOTES ON SKILL AUTHORING CONSISTENCY
===============================================================================

When writing each of the above, keep the pattern already established:

  • SKILL.md — core happy path, 5–7 sections:
      1. Scope & Boundaries (When to use / When not to)
      2. Structural Overview (objects + endpoints table)
      3. Core Workflow (step-by-step with code, 2–3 languages)
      4. Security Constraints — Never Violate
      5. Testing (sandbox test data)
      6. Useful Links

  • references/REFERENCE.md — deep dive:
      • Full endpoint map (method | path | purpose)
      • Field-level request/response tables
      • Per-language SDK code blocks (Node, Python, Java, Go at minimum)
      • Webhook payload schemas
      • Error codes

  • Frontmatter name + description — packed with trigger keywords so the
    skill actually gets loaded by the AI assistant on intent match.
    Look at migrate-from-razorpay.md for the density target.
